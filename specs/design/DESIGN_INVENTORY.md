## Notes / anomalies

- **`4d` is confirmed missing.** Bloco 4's header lists only 4a, 4b, 4c, 4e in the source file; no `dv-opt id="4d"` exists anywhere. This is a genuine gap in the design's own numbering (likely a skipped/removed screen concept), not an extraction error — the full Bloco 4 section (lines 12–232) was read end-to-end.
- **Status badge/semantic color vocabulary is consistent across all Blocos**: the same 5 hex families (green/amber/red/blue/neutral) recur for every status label regardless of domain (exam results, medication stock, vaccination status, appointment tags) — see DESIGN_TOKENS.md §1 for the canonical mapping.
- **The 4-state pattern (loading/empty/error/success)** documented in 1a is declared as the single reusable pattern for "toda lista, formulário e upload" across all 4 Blocos, but most individual screens (2b, 3d, 3e, 4b, 4e) show only their default/populated state in the mockup — loading/error states for these screens are implied by the shared pattern, not drawn per-screen. This is worth flagging to a human: confirming intent to reuse the 1a pattern verbatim (vs. designing bespoke states) avoids ambiguity during implementation.
- **Bottom nav labeling inconsistency**: the reference screen (1a) and in-app screens (2b, 2c, 3a, 3d, 4a, 4b) all show only 5 tabs (Início/Consultas/Exames/Remédios/Mais), with "Mais" apparently acting as an overflow hub reaching screens like 3e (Prevenção) and 4a (IA) — but 4a and 4b's bottom nav highlight "Mais" as active while 3e's does too, meaning "Consultas/Exames/Remédios/IA/Perfil/Prevenção" are not literally all top-level tabs; the exact contents/structure of the "Mais" menu itself is never shown as its own screen. A human decision is needed on what the "Mais" screen actually contains and how it routes to 3e/4a/4b/4c/4e.
- **Dynamic/templated colors** (many chip and toggle states use `{{ xBorder }}`/`{{ xBg }}`/`{{ xColor }}` bindings rather than literal hex, e.g. in 2a, 4b, 4c, 3f) are not defined in the visible markup — their actual selected/unselected values are inferred from the equivalent *static* examples elsewhere (e.g. 2e's non-interactive "Consulta" chip, 3g's selected "Comprimido" chip) and documented in DESIGN_TOKENS.md, but a human should verify these inferred values against the design tool's live state if available.
